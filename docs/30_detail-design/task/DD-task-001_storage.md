# DD-task-001 タスクと画像の端末内保存

## 1. 概要

BD-001、FR-002、FR-003、FR-004、NFR-AVL-001、NFR-AVL-002 に対応し、タスク・画像・リマインド停止設定・編集途中の一時データと撮影の一時結果を拡張機能オリジンの IndexedDB に保存する。リマインドの表示判定、撮影、画面操作およびコンテキスト間の通信は本書の対象外とする。

画面からのタスク保存は、画像の追加・削除・差し替えを含めて確定する。編集途中の一時保存は登録済みタスクを更新しない。

## 2. モジュール構成

以下は実装予定の論理構成であり、ファイルはまだ作成しない。

| ファイル                            | 役割                                             |
| ----------------------------------- | ------------------------------------------------ |
| `src/shared/task-types.ts`          | タスク、画像、停止設定、一時データの型           |
| `src/background/task-repository.ts` | IndexedDB の読み書き、トランザクション、入力検証 |
| `src/background/task-capacity.ts`   | 検証用の論理データ容量の計算                     |

IndexedDB は拡張機能オリジンで使用する。content script のページオリジンの保存領域にはタスクや画像を保存しない（REF-014）。

## 3. インターフェース

```ts
type TaskId = string;
type ImageId = string;
type DraftId = string;

interface TaskRecord {
  id: TaskId;
  url: string;
  hostname: string;
  name: string;
  dueDate: string | null;
  detail: string;
  completed: boolean;
  createdAt: string;
  reminderSuppressedUntil: string | null;
  revision: number;
}

interface ImageRecord {
  id: ImageId;
  taskId: TaskId;
  position: number;
  data: Blob;
}

interface DomainSuppressionRecord {
  hostname: string;
  suppressedUntil: string;
}

interface DraftFields {
  name: string;
  url: string;
  dueDate: string;
  detail: string;
}

interface Draft {
  id: DraftId;
  kind: "registration" | "edit";
  taskId: TaskId;
  baseRevision: number | null;
  fields: DraftFields;
  images: ImageRecord[];
}

interface ActiveOperation {
  id: string;
  generation: number;
  kind: "registration" | "edit";
  draftId: DraftId;
}

interface OperationRef {
  id: string;
  generation: number;
}

interface CaptureTemporaryRecord {
  requestId: string;
  owner: { kind: "registration" | "edit"; id: string };
  operation: OperationRef;
  status: "pending" | "ready" | "error";
  imageId: ImageId | null;
  image: Blob | null;
  errorCode: string | null;
  restorationFailed: boolean;
}

interface TaskRepository {
  getTask(
    id: TaskId,
  ): Promise<{ task: TaskRecord; images: ImageRecord[] } | null>;
  listTasks(): Promise<TaskRecord[]>;
  deleteTask(id: TaskId, expectedRevision: number): Promise<void>;
  startDraft(draft: Draft): Promise<OperationRef>;
  getActiveDraft(): Promise<{ operation: OperationRef; draft: Draft } | null>;
  saveDraft(operation: OperationRef, draft: Draft): Promise<void>;
  resumeDraft(operation: OperationRef): Promise<OperationRef>;
  discardDraft(operation: OperationRef): Promise<void>;
  commitDraft(operation: OperationRef): Promise<TaskRecord>;
  listDomainSuppressions(): Promise<DomainSuppressionRecord[]>;
  updateDomainSuppression(
    hostname: string,
    suppressedUntil: string | null,
  ): Promise<void>;
}
```

- ID は各レコードを識別する文字列とし、異なるタスク・画像・一時データ間で重複させない。
- `dueDate` は期限なしの場合 `null`、期限ありの場合 `YYYY-MM-DD` 形式の日付とする。`createdAt` は登録日時、`revision` は保存時に更新する版番号とする。
- `url` は HTTP・HTTPS の URL、`hostname` はその URL から正規化して得たホストとする。呼び出し側の `hostname` を無条件に信用せず、保存前に URL から導出して整合させる。
- `createdAt`、`reminderSuppressedUntil`、`suppressedUntil` は UTC の ISO 8601 形式（`YYYY-MM-DDTHH:mm:ss.sssZ`）で保存する。停止終了日時は設定時の端末の現地日時から確定した瞬間に変換し、タイムゾーン変更後も同じ瞬間を維持する。表示時は現在の端末の現地日時に変換する。
- 夏時間等により存在しない現地日時は再入力を求める。同じ現地日時が２回ある場合は、利用者に UTC オフセットを示してどちらの瞬間か選択してもらい、確定した瞬間を保存する。
- 画像は１タスクにつき10件まで、１件につき5,000,000バイトまでとする。`position` はタスク内の表示順とする。
- 新規登録時の `baseRevision` は `null` とし、保存済みの同一 ID がないことを確認して `revision` を1とする。既存タスクの編集時は読み込み時の `revision` を保持し、一致すれば1増加する。実際の版が一致しない場合は変更を拒否する。既存タスクの `createdAt` は変更しない。
- `updateDomainSuppression` は対象ホストと、変更後の停止終了日時または解除を表す `null` を受け取る。
- これらは拡張機能内部の論理インターフェースであり、Chrome メッセージのペイロード型ではない。`Blob` を Chrome メッセージに直接渡す設計ではない。

## 4. 処理詳細

1. IndexedDB に `tasks`、`images`、`domain_suppressions`、`edit_drafts`、`capture_temp`、`active_operation` の各ストアを作成する。各ストアのキーはそれぞれタスク ID、画像 ID、正規化ホスト、一時データ ID、撮影要求 ID、固定キーとする。`images` はタスク ID、`capture_temp` は所有者の種別と ID で取得できる索引を持つ。登録用の途中入力も `edit_drafts` に保存し、登録・編集の種別と対象を区別する。登録用データの型と操作ごとの API は後述の制限状態に合わせて確定する。
2. タスクの確定前にタスク名の必須、URL、期限の形式と実在日付、画像の所有タスク・件数・サイズ・ID・表示順の整合性を検証する。画像の表示順は0から始まる連番とする。検証に失敗した場合、確定の書き込みは行わない。編集途中の一時保存では未入力のタスク名を許容し、画像の所有タスク・件数・サイズ・ID・表示順の整合性を検証する。
3. タスクと画像の保存・削除は同一トランザクションで行う。変更時は現在の版を照合し、画像の削除・追加とタスクの更新をまとめて確定する。版が一致しない場合や書き込みに失敗した場合は全体を中止する。
4. 撮影前の編集内容は `edit_drafts` に一時保存する。一時保存が成功するまで撮影用タブを開かない。一時データには編集中のタスクと、追加・削除・差し替えを反映した画像一覧を含める。
5. 編集保存時は、一時データの `baseRevision` を照合し、タスク・画像の更新と一時データの削除を同一トランザクションで確定する。失敗時は既存タスクと一時データを保持する。取消時は登録済みタスクと画像を変更せず、一時データを削除する。
6. タスク削除時は対象タスクと画像を同一トランザクションで削除する。確認操作は呼び出し側が担当する。別の編集画面の一時データは削除せず、確定時に元タスクが存在しないことをエラーとして通知する。
7. ドメイン停止設定の変更・解除は `domain_suppressions` の `readwrite` トランザクション内で現在の全設定を読み、現在の PSL により基準ホストが同じ対象に属する設定を判定する。変更時は該当する全設定を更新し、該当がなければ指定ホストの設定を作成する。解除時は該当する全設定を削除し、ほかの設定は変更しない。同じストアへの書き込みはトランザクション単位で順序付けられるため、先に読み出した一覧で全設定を置き換えない（REF-030）。
8. IndexedDB のトランザクション中にネットワーク通信や別コンテキストへの応答を待たない。対象判定に必要なローカルの PSL データは操作前に準備し、読み書きが失敗した場合はトランザクションを中止する（REF-030）。

撮影した画像の一時結果は `capture_temp` に保持し、拡張機能画面から同じオリジンの保存領域を通じて取得する案とする（REF-014）。`pending` は未完了、`ready` は画像付きの成功結果、`error` は画像を含まない失敗結果とする。撮影と復元の両方に失敗した場合はエラー種別と `restorationFailed` の両方を保持する。編集時に画像の追加を確定する場合は、所有者を照合し、編集途中の画像一覧への移行と撮影結果の一時データ削除を同一トランザクションで行う。Chrome メッセージに `Blob` は含めない（REF-019）。一時結果の所有者認証・中断時の整理手順と、撮影側の詳細設計との整合は未決。

撮影結果の保存は、同じ要求 ID・所有者の `pending` の存在を同一トランザクションで照合してから行う。所有者が要求を無効にした後の遅延結果は書き込まない。編集の保存・取消に伴う `edit_drafts` と `capture_temp` の整理は同一トランザクションで行う案とする。撮影中断時のページ状態の復元確認は IndexedDB の確定とは別であり、その結果の通知と整理手順は未決（DD-capture-001）。

`DraftFields` は入力途中の空文字や不正な URL・期限を文字列のまま保持する。登録時は確定前に割り当てたタスク ID を途中画像の `taskId` に用い、編集時は既存タスク ID と元の版を保持する。タスクとして確定するときに必須・形式・画像を検証する。保存可能な文字数は未決であり、制限を超える入力を黙って切り詰めない（DD-task-002）。

### 登録・編集の制限状態と再開

1. `active_operation` の固定キーにある状態は0件または1件とする。登録・編集の開始は同ストアと `edit_drafts` を含む `readwrite` トランザクションで、状態がないことの確認、操作 ID の生成結果、世代1と初期途中入力の保存を一体で確定する。競合して後に実行された開始は既存状態を検出して拒否する。途中入力の保存が失敗した場合、操作を開始したと扱わない。
2. 完了・未完了、削除、停止設定の変更は `active_operation` と変更先の全ストアを含む同一 `readwrite` トランザクションで状態がないことを確認してから変更する。登録・編集の保存は同ストア内の操作 ID と世代を照合し、対象の更新、途中入力と関連一時結果の削除、制限状態の解除を同一トランザクションで確定する。検証・版照合・書き込みの失敗ではすべて中止する。
3. 途中入力の保存、撮影結果の反映、取消・破棄でも同一トランザクション内で現在の操作 ID と世代を照合する。取消・破棄は途中入力と関連する撮影結果の無効化・削除、制限状態の解除を一体で確定する。解除後に届く旧操作の要求は拒否する。進行中の撮影やページの復元を IndexedDB の確定だけで完了とみなさない。
4. 画面終了や Service Worker・Chrome の停止では制限状態と保存済み入力を削除しない。利用者が再開したとき、操作 ID を維持したまま世代をトランザクション内で増やし、再開前の世代からの遅延書き込みを拒否する。再開処理と旧世代の処理は同じ `active_operation` を含むトランザクションで順序付け、先に確定した内容を保持する。同じトランザクションで確定済みの撮影結果が操作に属することを照合し、その世代を新しい世代へ更新して維持する。未完了の旧世代の撮影は無効化する。撮影の中止・復元が確認できなければその旨を表示する。世代の更新に失敗した場合は再開を成功扱いにしない。
5. 画面は入力変更ごとに一時保存を要求し、同じ世代内では入力順に処理する。画面が保存完了前に閉じた場合は最後に保存成功した内容だけを再開する。保存の失敗時は理由と未保存状態を画面に示し、入力を保持する。複数画面での再開、破棄、保存と旧世代の遅延要求を実機で検証する。
6. 同期的な状態変更も含め、タスク・画像・停止設定を変更するすべての経路が `active_operation` を含むトランザクションで制限を確認する。画面上のボタン制御や Worker のメモリ内フラグだけで制限しない。撮影結果の保存・反映には `active_operation` と `capture_temp`、必要な途中入力ストアを含め、操作 ID・世代と要求状態を同一トランザクションで照合する。

### 停止終了日時の変換案

1. 画面で入力された現地の日付・時刻の各要素を、暦上の存在しない日付や範囲外の時刻を補正せず検証する。時刻は分単位で入力し、入力時の秒・ミリ秒は0とする。許容する日付の範囲は未決。
2. 端末の現在のタイムゾーン識別子を `Temporal.Now.timeZoneId()` で取得し（REF-033）、入力した現地日時と組み合わせる。`Temporal.ZonedDateTime.from()` の `overflow: "reject"` と、それぞれ `disambiguation: "earlier"` / `"later"` を使い、早い候補と遅い候補を求める案とする（REF-032）。
3. 各候補を同じタイムゾーンの現地日時に戻し、入力の年月日・時刻の全要素と一致するものだけを残す。同じ瞬間の候補は重複を除く。候補が0件なら存在しない現地日時として再入力を求める。1件ならその瞬間とし、2件ならそれぞれの UTC オフセットを表示して利用者に選択させる。想定外の結果や変換エラーは成功扱いにしない。
4. 確定直前に端末のタイムゾーンを再取得し、候補の作成時と異なる場合は候補を破棄して再計算し、利用者に再確認を求める。確定した瞬間は、保存形式 `YYYY-MM-DDTHH:mm:ss.sssZ` で丸めずに表現できる場合に UTC に変換する。表現できない場合は更新せず、理由を表示する。表示時は保存した瞬間を現在の端末のタイムゾーンに変換する。
5. `Temporal` を利用できない場合やタイムゾーンの取得・変換に失敗した場合は、日時を推測せず停止設定を更新しない。Chrome 144 で `Temporal` が導入されているが（REF-034）、対応環境での利用可否、端末のタイムゾーン取得、型定義および変換結果は後工程で検証する。
6. 設定・変更時は保存処理の `readwrite` トランザクション内で端末の現在時刻を取得し、選択した瞬間がそれより後であることを確認する。現在以前の場合は更新せず再入力を求める。トランザクションの確定前に終了日時を過ぎた場合は、保存成功後に停止期間が終了済みとなり得る。解除には終了日時を要求しない。

候補を計算してから保存が確定するまでに端末設定が変更される場合の扱い、および UTC 保存形式で表現できる日付の入力範囲は未決。

`Temporal.ZonedDateTime.from()` の公式仕様では、`earlier` / `later` による重複・欠落日時の解決と `overflow: "reject"` が定義されている（REF-032）。ただし、候補を現地日時へ戻す本案の判定結果、型定義、端末のタイムゾーン変更を含む動作は実機で検証していない。

### データベースの版管理・復旧案

初回は版1としてストアと索引を作成し、以後のスキーマ変更ごとに版を上げる。`upgradeneeded` 内で旧版から必要な移行を順番に適用し、移行処理が失敗した場合は更新を確定しない（REF-036、REF-038）。各画面と Service Worker は `versionchange` を受けた場合、新たな読み書きを開始せず接続を閉じ、必要に応じて再接続する（REF-037）。

現在の実装は版1である。単一操作制限の導入時は版2で `active_operation` を追加し、既存タスク・画像・停止設定を保持する。初回作成では版2の全ストアを作成する。版1からの更新では旧 `edit_drafts` と `capture_temp` の件数を移行トランザクション内で確認する。どちらも0件なら既存ストアを保持したまま `active_operation` を追加して版2を確定する。

どちらかに旧形式のデータがある場合、その内容や所有者を推測せず、版更新を中止して版1と全データを保持する。画面には一時データを移行できず操作を開始できないことを表示し、自動削除・初期化しない。原因を区別できるエラーコードを返す。旧形式のデータを利用者が確認・復旧する手順は別途設計する。現在の版1実装にこれらの一時ストアを書き込む経路はないが、件数が0であると決めつけない。

別の接続により移行が `blocked` となった場合は、利用者に拡張機能画面を閉じて再試行するよう表示する（REF-039）。上位版を読み取れない、移行できない、またはデータの読み込み・整合性確認に失敗した場合はエラーを表示し、空の一覧として扱わない。データベースの自動削除・初期化は行わない。破損原因の特定、利用者への復旧手順と各バージョンの具体的な移行内容は未決。

### 容量の確認

NFR-AVL-001 の検証では、各タスクの `TaskRecord` を上記のフィールド順に JSON 化した UTF-8 バイト数と、各画像の `id`・`taskId`・`position` をこの順に JSON 化した UTF-8 バイト数、各画像 Blob のバイト数を合計する。配列の区切り文字、IndexedDB の内部管理領域、一時データ、ドメイン停止設定は含めない。この値は検証のための論理容量であり、端末の実際のディスク使用量ではない。

画像を１タスク10件以下、１件5,000,000バイト以下にして複数タスクに登録し、不足分を ASCII 文字のタスク詳細で調整することで合計100,000,000バイトの検証データを用意する。保存後に全タスク・画像を読み出し、内容と容量を再確認する。検証開始時の保存領域は空とし、必要な空き容量を確保する。100,000,000バイトを超えたことだけを理由に保存を拒否しない。

## 5. 状態遷移

| 対象   | 遷移                        | 条件                                                 |
| ------ | --------------------------- | ---------------------------------------------------- |
| タスク | 未登録 → 登録済み           | 入力検証とトランザクションが成功                     |
| タスク | 登録済み → 更新済み         | 版が一致し、トランザクションが成功                   |
| タスク | 登録済み → 削除済み         | 利用者が確認し、トランザクションが成功               |
| 編集   | 編集中 → 一時保存済み       | 撮影前の一時保存が成功                               |
| 編集   | 一時保存済み → 確定         | 版が一致し、タスク・画像の更新と一時データ削除が成功 |
| 編集   | 一時保存済み → 取消         | 一時データの削除が成功                               |
| 編集   | 一時保存済み → 一時保存済み | 保存に失敗、または版が不一致                         |

## 6. エラー処理

| エラー                     | 検知方法                                     | ユーザーへの表示                             | ログ           |
| -------------------------- | -------------------------------------------- | -------------------------------------------- | -------------- |
| 入力不正・画像上限超過     | 保存前の検証                                 | 対象項目と理由を表示                         | エラー種別のみ |
| 版の不一致                 | トランザクション内で版を照合                 | 更新競合を表示し、入力を保持                 | エラー種別のみ |
| 容量不足・書き込み失敗     | IndexedDB の要求またはトランザクションの失敗 | 保存できなかった理由を表示し、入力を保持     | エラー種別のみ |
| データの読み込み失敗       | IndexedDB の要求の失敗                       | 読み込めなかったことを表示                   | エラー種別のみ |
| 一時データの保存・削除失敗 | IndexedDB の要求またはトランザクションの失敗 | 操作が完了していないことを表示し、入力を保持 | エラー種別のみ |

保存や削除に失敗した場合、成功として扱わない。競合時の再読み込み・入力の統合操作は未決。

## 7. ログ出力

エラー種別のみを記録し、タスク名・詳細・URL・ホスト・画像・一時データを出力しない。正常な操作ではタスク内容や画像をログに出力しない。

## 8. テスト観点

- 正常系: 登録、編集、完了・未完了、画像の追加・削除・差し替え、確認後の削除、停止設定の保存、Chrome 再起動後の再表示。
- 正常系: 一時保存からの編集再開、確定時の一時データ削除、取消時に登録済みタスクが変化しないこと。
- 正常系: 撮影結果を拡張機能オリジンで受け取り、編集途中の画像への移行と一時結果の削除を同時に確定すること。
- 異常系: 保存途中の失敗時にタスクと画像が部分更新されないこと、撮影結果の移行失敗時に一時結果が保持されること、版の不一致、一時保存失敗、容量不足、読み込み失敗。
- 異常系: 撮影要求の無効化と完了の競合、編集取消時に登録済みデータが変わらないこと。
- 異常系: 版更新時に別画面が接続中の場合の通知、移行失敗時に以前のデータを勝手に消去しないこと、未対応の上位版を空データとして扱わないこと。
- 異常系: 同時にドメイン停止設定を変更・解除した場合に、無関係な設定や先行する変更が失われないこと。
- 日時: タイムゾーン変更後も停止終了の瞬間が変わらないこと、存在しない現地日時を拒否すること、重複する現地日時で選んだ瞬間を保存すること。
- 日時: `America/New_York` の 2024-03-10 02:05 は候補0件、2024-11-03 01:05 は UTC-04:00 と UTC-05:00 の2候補、通常時刻は1候補となること。候補作成後に端末のタイムゾーンが変わった場合は再確認を求めること。
- 日時: 選択した終了の瞬間が保存時の現在時刻より後の場合に設定され、同時または過去の場合は更新されないこと。
- 境界値: 画像10件と11件、5,000,000バイトと5,000,001バイト、合計100,000,000バイトの保存・再表示。
- セキュリティ: 入力内容や画像がログに含まれず、content script の保存領域に書き込まれないこと。
